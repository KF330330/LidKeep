# 1.0.1 安装失败修复

2026-09-16 的首次真实安装在 postinstall 阶段失败：`lidkeep.service --restore` 被系统以 SIGKILL 终止。系统日志同时记录 AMFI `-423` 与 Gatekeeper execution rejection。程序文件已复制到目标位置，但两个 LaunchDaemon 尚未注册，`SleepDisabled` 仍为 0。

这是交付验证遗漏：1.0.0 只检查了包内容和静态代码签名，没有实际执行解包后的可执行文件。静态检查通过不能证明系统允许启动。

复现确认：已安装 helper 与包内 helper 字节完全一致、签名有效，但执行被拒；对解包文件原位重新签名也无效。用 Apple `install` 创建全新的文件、保持字节与签名不变后，可以正常执行；原子替换回原路径后仍可执行。差异与包提取文件的系统策略状态有关，并非 Swift 程序崩溃或系统路径权限错误。

1.0.1 的安装和恢复脚本先进入维护状态，在管理员拥有的目标目录创建本机副本，检查普通文件、单硬链接、所有权、权限、字节一致与代码签名；后台副本还必须在替换前通过只读启动自检，然后才原子替换。实验中，仅创建新 inode 后直接替换仍可能被拒，先执行副本的自检再替换才通过完整流程，因此保留这一步作为必需条件。只允许本工具的两个固定可执行文件；不修改 Gatekeeper、SIP 或隔离属性，不添加系统放行规则。XPC 使用的代码签名哈希保持不变。

失败安装后重试时，preinstall 在运行已有 helper 前也执行同样步骤，避免旧文件阻止修复安装。App 增加无界面、无登录注册、无 XPC 的 `--self-check` 参数。打包检查在临时解包目录复用实际安装函数，并执行 App 自检和 helper 的只读 `--diagnose`。

本次修复少于 100 行代码增删，低于全局规则的新一轮 Claude 审查门槛；执行了独立诊断和针对安装路径的回归验证。真实管理员安装与后台启动仍以安装完成后的系统日志和 launchd 状态为准，不能由临时目录自检替代。

Apple 对静态签名与 Gatekeeper 执行检查的区分参见 [Resolving Gatekeeper Problems](https://developer.apple.com/forums/thread/706379)。
