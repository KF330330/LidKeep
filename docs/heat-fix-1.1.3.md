# 1.1.3：合盖发热事件与故障恢复修复

## 问题观测

一次约两小时的电池供电合盖期间，系统整体 CPU 负载较高（来自其他计算任务），内存压力正常、未使用交换区。采样不能读取全部系统进程，也不包含 GPU 功耗或机身表面温度，不能认定已找全热源。

LidKeep App RSS 峰值 107.6 MiB，CPU 峰值 0.3%；两个后台 RSS 峰值分别为 26.2 MiB、18.7 MiB。未见 LidKeep 本体内存暴涨，但故障保护确实失效：整个合盖时段实际休眠状态未知，报 Bad file descriptor。排查开始时系统实际 SleepDisabled=1。

现场保留的两个后台分别积累了 1,763、2,552 个 PIPE 项；标准输入、输出、错误描述符都指向有效的 /dev/null。独立只读复现中，旧版每次调用后遗留一个描述符，96 次读取后从 6 个增至 102 个；修复版在 128 个描述符软上限下连续 1,000 次读取，始终保持 3 个。

系统热状态最高为 fair，未达到现有 serious/critical 阈值。机身很烫不能被 nominal/fair 排除。此次不擅自更改热阈值，也不把系统热状态当作表面温度计。

## 修复行为

- 每次 pmset 调用显式关闭管道，并在局部 autoreleasepool 内释放 Foundation 对象；检查 fcntl/read 错误、限制读取量和进程退出等待。
- 具有可信接管记录时直接恢复 disablesleep=0，再读回确认；读取故障不会阻断恢复尝试，恢复未确认时保留接管记录。
- 实际状态读取失败会清除 GUI 租约、发布停止保活状态并尝试恢复，不再只改变菜单上的状态文字。
- 安全记录或策略写入失败不再跳过电源恢复。恢复未确认时，新心跳不能重新启用保活；确认后仍遵守原有恢复等待。
- 独立监护连续三次恢复失败后退出，由 launchd 重新拉起，以释放坏进程资源；启动仍先恢复遗留设置。
- 本次升级保留 A35 App 图标和 M03 菜单栏图标；本机安装完成后已确认保活为手动关闭并持久保存，SleepDisabled=0。

## 验证

96 项 XCTest 全部通过，其中新增 10 项覆盖句柄、可信接管恢复、故障状态撤销、元数据失败与监护重启。所有真实电源回归调用均为只读 pmset -g，写入路径使用替身；低描述符上限下另外执行了旧版 96 次、新版 1,000 次独立对照。安装包通过签名、身份要求、root:wheel 归属、图标及本机执行检查。

没有再用发热中的电脑进行合盖压力测试；自动低电量与 serious/critical 保护的模拟测试仍通过，不能据此保证密闭包内安全。

## 一轮 Claude 跨模型审查

使用本次修改前的完整工作树快照作为独立审查基线，避免混入已完成但尚未提交的旧任务。按电源调用、故障恢复两模块分拆，每份小于 500 行。两份结论均为“未发现严重问题”，没有须修复的严重项；未进行复审。

审查者提出四项疑问，处理如下：

1. 句柄修复不能证明全部发热原因：认可限制。报告分别列出后台资源泄漏和合盖计算负载，不宣称修复后不会发热。
2. restore 单元测试不能单独证明休眠路径：已有 sleepLocked 的恢复失败阻断、回执去重以及热/低电量保护测试，整套同时通过。
3. 主服务没有与监护对等的自我重启：暂不扩大改动。主服务故障会持续停止保活，监护负责恢复；安装修复版会替换并重启两个旧进程。后续非本次泄漏引起的主服务故障可能仍需维护重启。
4. 外部工具占用 SleepDisabled 时的恢复提示较笼统：未改。该情形继续停止保活、不接管其他工具；属于已有行为，未影响此次安全修复。

Claude 的只读审查完成后，外部 Stop hook 把工作区既有未提交修改误认为审查会话产生的代码；原始审查结论已从输出保存，不写豁免或放行标记，也不启动互相复审。

原始测试输出与进程记录属于本地过程记录，未随公开仓库发布；完整个人进程记录保留在用户 Library/Application Support/LidKeep/Diagnostics，本仓库不复制原始进程清单。
