用户要求在以后合盖运行时同步记录、排查内存消耗。本次新增本机自动采样、手动检查、有限容量归档与诊断窗口，未更改电源保护策略。

任务后缀：lidkeep-diagnostics-20260916。任务起点 5f091c7dc398d5297b6ed4b7e27a31b79eba65b3。原始需求单独落盘，首次审查 diff 按采样、归档、报告、App、后台五个模块拆分，各不超过 500 行。调用本机 Claude Code / sonnet 进行只读首轮审查。修复后的代码未送回复审。

## 已核实意见

- Archive P1 成立并修复：接近总容量时，恢复较早报告会为新报告腾出空间，可能删除同一恢复列表中后续的段。恢复循环现跳过已清理的文件，仍拒绝权限或链接异常。16 段合计恰好 32 MiB 的回归用例在修复前失败、修复后通过。
- Archive P2 未采纳：关于每次归档配额检查成本过大的判断缺乏实际证据。20 段历史、40 次 append 的本机测量中位数约 1.1 ms，40 次累计 CPU 约 45 ms；保留有界配额检查，避免引入额外缓存状态。数据只说明此次本机测量，不保证未来延迟。
- Report P1 不成立：审查将既有 caffeinate 服务误认为 LidKeep 子进程。当前三个进程是 LidKeep、lidkeep-daemon、lidkeep-watchdog，两个管理员后台经已验证状态接口自报；LidKeep 没有启动或接管那两个 caffeinate 服务。
- Service P1 作为关键测试缺口采纳：保持判断逻辑不变，提取并直接测试 watchdog 计数的同启动周期、0/15 秒边界、过期、未来、缺失数据，以及不替换 daemon 计数。
- 采样器的 Mach 时钟单位与服务生产端一致；调用在诊断串行队列内。ThermalLevel 仅含 nominal/fair/serious/critical/unknown，未知值在排序前过滤。Watchdog 定时器为 5 秒；15 秒诊断新鲜度与 30 秒保活租约不同。

- App P1 不成立：applicationDidFinishLaunching 首先同步调用 buildMenu()，随后才注册回调并启动 diagnostics；菜单项初始化不依赖后台首次回复。审查根据局部 diff 推断菜单由 render 回调构建，与完整代码不符。
- App P2 作为关键测试缺口采纳：新增 5 个直接驱动 DiagnosticsController 的测试，覆盖合盖开始、30 秒采样、开盖结束、关闭持久化、休眠唤醒分段、手动互斥和失败恢复。使用真实串行队列、真实临时归档，注入外部读数；生产默认行为保持一致。

本轮 5 个模块均已获得首轮结论：修复 1 个归档缺陷，补齐 2 类关键测试，未采纳 3 条与事实或实测不符的意见。

Claude 的全局停止钩子误把工作区改动当作审查者自己的代码，导致部分 CLI 最后输出被钩子追问覆盖。原始审查文本已从对应会话记录保存。尚未返回结论的模块仅继续或重试原始材料；没有将修复 diff 复审。
