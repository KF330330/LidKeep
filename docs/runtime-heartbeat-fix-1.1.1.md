# 1.1.1：读取监护心跳之后再核对时间

1.1.0 安装后的手动诊断已经正常生成三个本程序进程的资源数据，真实报告窗口也完成了截图检查。复查同时观察到后台反复从 active 进入 recovering，原因标为独立监护失联；这些恢复事件在升级前亦已存在。

代码存在明确的取样顺序竞态：SystemSampler 构造 Environment 时先取单调时间，之后仍读取盖子和显示器；Daemon 稍后读取可能刚被更新的 guardian.json，却用早先的 Environment.now 判断该心跳是否来自未来。正常新心跳可能被误判，触发停止保活及 60 秒恢复等待。诊断状态合并也有同样的先后顺序问题。

修复改为先读取 guardian，再取得当前单调时间核对其新鲜度。继续拒绝真正未来时间、超过租约、错误启动周期和带错误的心跳；不放宽低电量、温控或失联保护阈值。GUI 心跳在同一串行队列更新，Watchdog 读取 desired 后才取环境时间，无同类顺序问题。

此前日志没有记录被拒心跳的具体时间差，能确认代码竞态并解释此类现象，不能断言历史每一次恢复或过热都由它引起。旧日志中的 Bad file descriptor 和命令超时属于其他线索，此次不凭上述竞态将它们一并宣布修复。

现场修复独立计数小于 100 行代码增删；按全局规则不再触发一轮 Claude 复审。1.1.0 诊断主体的五模块首轮审查见 review-diagnostics-1.1.0.md。

86 项测试通过，包括新增的读取与时钟调用顺序、真实未来/过期/错误心跳拒绝回归。1.1.1 保留 1.1.0 的诊断入口和全部原有设置。
