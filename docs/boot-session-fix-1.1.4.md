# 1.1.4：后台重启后保活失效与休眠事件漏记

## 问题现象

合盖后 Claude Code 会话再次中断，界面提示 `Please run /login · API Error: 403 Request not allowed`。该提示本身不能确定进程退出或认证失败的具体原因。

系统电源日志显示合盖期间进入 Clamshell Sleep，开盖时才唤醒。排查时 LidKeep 1.1.3 App 和两个后台均存在，持久开关 enabled=true，但实际 SleepDisabled=0。主服务与监护服务缓存的 boot 值（kern.boottime）彼此不同，当前 kern.boottime 又已变化。两个服务因此无法满足同次开机身份检查，主服务反复进入故障和恢复等待，保活未恢复。

kern.boottime 是可随系统时钟校正变化的时间值，不适合作为跨进程重启的开机身份。内核另行提供每次开机唯一的 kern.bootsessionuuid。本次不更改系统时间，也不把休眠与后续 HTTP 403 的完整因果链视为已经证实。

## 修改

- 两个后台统一读取内核 boot session UUID；读取或格式验证失败则拒绝启动保活，不回退到不可靠身份。
- 旧身份下尚未消费的休眠请求不会作为新身份请求重放；安装仍先恢复原休眠设置，再重启两个后台。
- 自动诊断新增系统休眠和唤醒事件记录，覆盖“系统先休眠，五秒合盖轮询尚未开始记录”的路径。只保存事件处理时的真实观测，允许合盖状态未知，不填补休眠期间的数据。通知异步处理，不能保证系统一定在休眠前完成采样。
- 保留手动关闭、温控、电量、心跳保护及 A35/M03 图标。

## 验证

最终 109 项 XCTest 通过，包括新增开机身份、旧休眠意图隔离、休眠先于轮询、未知合盖状态、重复通知、关闭自动诊断、唤醒后的报告入口与重启恢复、独立事件保留额度、容量淘汰及旧记录兼容的覆盖。真实电源写入用替身；本机传感器与内核 UUID 读取、最终安装包签名、身份清单、root:wheel 归属和可执行文件检查通过。

本机已安装 1.1.4（build 9），安装器返回 upgrade successful。持久开关仍为 enabled=true，原机器验收标记仍为 verified=true；新版 App PID 76571 已重新连接后台。首次安装后实际进入 active，两个后台 boot 与内核 UUID 一致，SleepDisabled=1。

随后只重启独立监护（PID 从 71335 变为 87019）。launchd 在卸载后立即 bootstrap 返回一次 I/O 错误；只读确认旧任务已卸载后重新 bootstrap 成功，没有改权限或绕过安全检查。重启初期记录 mode=recovering、SleepDisabled=0、无 ownership；等待既有 60 秒恢复条件后，再次记录 active、wantsAwake=true、SleepDisabled=1，safety 已清空，两个后台仍为同一 UUID，原恢复 baseline=0。期间未请求整机休眠，也未修改或关闭任何 Claude/Codex 会话。

已安装 App 的独立命令行诊断生成两帧真实资源报告，采样耗时约 6–8 ms；菜单栏 App RSS 约 95 MiB、该秒 CPU 0%，系统内存压力 normal。该短时检查只验证采样与报告可用，不能代表长时合盖表现。

受影响 Claude Code 会话的再次合盖运行仍需用户现场复测；本修复不修改 Claude 账号、凭据或会话，未宣称 HTTP 403 已消失。安装包 SHA-256：`bdf574bd5df0c463ffb5e8bc5e57c7e3b258943b004dca657448a5b9aa693b29`。

## 一轮 Claude 跨模型审查

使用任务开始前的提交，提交本次 248 行 diff 与原始需求供只读审查。结论为两项问题（P1、P2）及两条疑问；审查原文属于本地过程记录，未随公开仓库发布。本轮不复审。

- P1 成立：唤醒单次快照会盖过菜单中的合盖报告。改为优先最新的非唤醒报告，仅没有其他记录时返回唤醒报告，重启后同样适用。
- P2 成立：频繁休眠／唤醒挤占原 20 段记录额度。系统事件改为独立 8 段额度，仍受 7 天与合计 32 MiB 限制，容量不足优先清理事件。
- 异步通知疑问：采样已有最多 4,096 进程与 2 秒扫描工作预算，但不能保证操作系统挂起前落盘；已明确单次观测发生在通知处理时，不保证休眠前完整快照。
- 休眠补采不一致疑问：接受改进，已有合盖记录在处理休眠通知时也补采一次；未知／过期电源上下文仍如实标记。
